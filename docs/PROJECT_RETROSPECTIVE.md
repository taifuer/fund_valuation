# 全球资产看板项目复盘

本文记录全球资产看板从一个 QDII 基金估值页面，逐步演进为包含多市场行情、基金估算、收益与风险分析、后台数据流水线和生产部署能力的完整小型应用的过程。

它不是提交记录的重述，也不是产品宣传文案。重点是保留项目中可复用的技术决策、失败经验、功能取舍和验收方法，供后续维护、重构以及类似数据看板项目参考。

## 1. 项目是否算从 0 到 1

从产品和工程闭环来看，可以认为这是一个从 0 开始完成的项目。

初始目标比较窄：读取公开行情，根据少量 QDII 基金的前十大持仓，估算基金当天可能的净值涨跌。最初的主要复杂度集中在浏览器端，数据也以请求时获取为主。

最终项目已经具备以下完整链路：

- 多市场指数、资产、ETF 和基金配置
- 当前行情、市场状态、历史日线与官方净值
- QDII 基金持仓、汇率和日期对齐估算
- 概览、基金、收益、风险、关于和内部诊断页面
- Flask API、SQLite 持久化和独立刷新 Worker
- 缓存、快照、历史增量更新、备份和清理
- 管理令牌、诊断令牌、限流和输入校验
- 单元测试、浏览器测试、Docker 验收和 GitHub Actions CI
- Nginx、Gunicorn、Worker 三容器生产部署

它仍不是专业行情终端，也不能替代基金管理人披露，但已经形成了可部署、可持续更新、可诊断、可维护的完整应用。

## 2. 演进过程

### 2.1 第一阶段：单页基金估值

项目最初只解决一个问题：国内 QDII 基金官方净值披露较晚，能否使用基金披露持仓和海外市场行情，提前观察当天方向。

这一阶段形成了基础能力：

- React 卡片展示基金名称、代码、官方净值和估算涨跌
- 根据前十大持仓加权计算估算结果
- 引入美元兑人民币汇率修正
- 判断 A 股、美股和港股交易时段
- 显示 LIVE、已收盘等状态
- 使用红涨绿跌的国内市场配色习惯

初版很快可用，但暴露出一个根本问题：行情、净值、历史和状态都在页面打开时获取，浏览器承担了过多数据编排责任。

### 2.2 第二阶段：扩展市场和历史数据

随后逐步加入：

- 纳指100、标普500、道琼斯等指数及对应期货参考
- 恒生指数、日经225、韩国 KOSPI、台湾加权
- 黄金、白银、原油和比特币
- A 股行业 ETF 与指数 ETF
- 基金官方历史净值和每日净值表
- 指数、资产和 ETF 历史走势
- 1周、1月、3月、半年、1年、3年、5年、今年和全部等区间

历史数据加入后，项目不再只是实时卡片页面，开始具备数据产品属性。与此同时，浏览器实时抓取、重复请求和历史数据临时加载的问题变得更加明显。

### 2.3 第三阶段：引入 Flask 和 SQLite

项目从纯前端数据编排迁移为 React 前端加 Python 后端：

- Flask 统一代理公开数据源，解决跨域、编码和接口格式差异
- SQLite 保存基金净值、市场日线、持仓、汇率和缓存
- 历史页面优先读取本地数据库
- 增量回填脚本负责补齐历史数据
- 新增基金后由后端校验并抓取资料、历史净值和持仓

这一阶段最重要的变化，不是更换技术栈，而是明确了职责边界：浏览器负责呈现和交互，后端负责数据接入、标准化和持久化。

### 2.4 第四阶段：页面拆分和分析能力

随着资产数量增加，单一首页无法兼顾快速浏览和深度分析，因此增加了独立页面：

- 概览页：优先展示市场和简化基金净值
- 基金页：展示日期明确的官方净值、待公布估值和实时参考
- 收益页：比较最新、今年及多个历史区间收益
- 风险页：比较最大回撤、收益回撤比和胜率
- 诊断页：受令牌保护，查看快照、缓存和覆盖度
- 关于页：说明项目、数据来源、反馈方式和重大更新

路由从组件内状态切换升级为可直接访问和刷新的 URL，筛选条件也写入查询参数，便于分享和恢复。

### 2.5 第五阶段：后台刷新和生产可靠性

线上部署后，真实延迟成为主要矛盾。项目进一步改成：

- 独立 Worker 按市场状态持续刷新
- 核心看板请求优先只读取 SQLite 或持久化快照，少量管理操作保留受控的上游补充
- 完整看板数据原子发布，避免同一页面混用不同批次数据
- 历史、持仓、资料、备份和清理任务与行情刷新解耦
- 非交易时段自动降低请求频率
- Docker Compose 管理 frontend、backend 和 worker
- GitHub Actions 验证测试、构建、Docker、健康接口和 SPA 路由

最终形成的核心原则是：允许服务器数据比上游慢一两分钟，但页面请求本身必须快、稳定且不依赖上游即时可用。

## 3. 最终架构

```text
浏览器
  |
  v
Nginx 前端容器
  |  React 静态资源
  |  /api 反向代理
  v
Gunicorn + Flask 后端
  |
  v
SQLite 当前快照、历史序列、持仓、汇率和缓存
  ^
  |
Python Worker
  |
  +-- 新浪财经
  +-- 东方财富 / 天天基金
  +-- TWSE
  +-- Naver Finance
  +-- ECB 历史参考汇率
```

### 3.1 前端职责

- 页面路由、筛选、排序和折叠状态
- 卡片、表格、图表和详情交互
- 对后端快照进行轻量解析和兼容降级
- 根据页面按需加载代码和数据
- 根据视口提供桌面与移动端布局

前端不应承担：

- 请求时逐个抓取上游基金接口
- 为历史页面临时补抓全量数据
- 判断复杂的上游缓存是否应刷新
- 保存跨用户共享的历史序列

### 3.2 Flask 后端职责

- 提供稳定、版本化的内部 API
- 标准化不同公开接口的编码和字段
- 读取 SQLite 快照和历史数据
- 执行基金代码强校验、令牌校验和限流
- 暴露健康、就绪、公开状态和内部诊断接口
- 在兼容场景下提供受控的上游兜底

### 3.3 Worker 职责

- 根据市场时段自适应刷新行情
- 定期刷新基金净值和资料
- 每天维护持仓行情日线和历史汇率
- 检查最新季度持仓并更新估算输入
- 生成完整看板和基金估值快照
- 增量维护市场和基金历史数据
- 执行备份、缓存清理和 SQLite 在线优化

### 3.4 SQLite 的定位

SQLite 不是临时缓存文件，而是单机部署的数据中心：

- 保存官方基金净值和市场日线
- 保存季度持仓及对应报告期
- 保存当前行情和完整看板快照
- 保存估值结果、误差对账和校准状态
- 保存可再生成的上游响应缓存
- 支持在线备份、迁移、恢复和完整性检查

对于当前访问规模，SQLite 比引入独立数据库服务更简单、更可靠。只有在多机写入、高并发分析或数据量显著增长时，才有必要迁移到 PostgreSQL 等服务。

## 4. 数据源策略

项目没有找到一个覆盖所有市场且稳定、免费、无需代理的数据源，因此采用按市场分工的多源策略。

| 数据 | 主要来源 | 用途 | 主要局限 |
|------|----------|------|----------|
| A 股、港股、美股行情 | 新浪财经 | 当前价格、涨跌和主要指数 | 字段未正式承诺，偶尔返回零值、旧时间或缺失字段 |
| 全球期货和资产 | 新浪财经外盘期货 | 现货闭市参考、黄金白银原油 | 合约与现货有基差，涨跌基准可能是结算价 |
| 基金净值、资料、持仓 | 东方财富、天天基金 | 官方净值、规模、费率、申购状态、季度持仓 | QDII 披露有延迟，接口有频率限制和格式变化 |
| 台湾指数历史 | TWSE | 台湾加权日线 | 官方接口按月返回，需要增量拼接 |
| 韩国指数与日韩个股 | Naver Finance | KOSPI 历史、日股和韩股当前行情及日线 | 不是承诺稳定性的正式开放 API，日本行情通常有延迟 |
| 历史参考汇率 | ECB | 跨净值日人民币口径换算 | 不是盘中实时汇率，需要按币种和日期换算 |

### 4.1 数据源接入原则

1. 先验证生产服务器能否稳定直连，而不是只在本地验证。
2. 当前行情、历史行情和交易日历要分别评估，不能因当前价格可用就认为历史也可用。
3. 上游原始字段必须转换为内部结构，页面不能直接依赖第三方字段顺序。
4. 每条行情尽量保留来源、原始时间、北京时间和抓取时间。
5. 任何兜底都必须能识别来源，不能把期货、旧缓存或其他市场代码伪装成现货。
6. 错误数据比暂无行情更危险，异常值应拒绝入库并保留最近一次有效快照。

### 4.2 外部分析如何使用

开发过程中参考过其他模型对加载链路的分析，也参考过公开行情页和同类 QDII 估值工具的展示方式。这些内容适合发现线索，但不能直接作为结论。

例如，外部性能分析曾指出批量大小、基金净值串行请求、代码分割和压缩等问题。真正实施前仍需核对：

- 后端是否已经支持更大的批量
- 压缩是否已由生产反向代理启用
- 浏览器 preconnect 是否真的能连接到由后端访问的上游
- 某个慢请求是网络等待，还是页面重复请求和缓存未命中

可复用的做法是：把外部建议当作待验证假设，结合代码、浏览器 Network、服务器日志和接口计时确认后再改。

## 5. 市场时间和状态

多市场项目最容易被低估的复杂度不是价格解析，而是时间。

### 5.1 统一北京时间，但保留市场语义

界面统一显示北京时间，内部仍需知道每个市场的本地时区和交易时段：

- A 股和港股存在午间休市
- 美股交易日跨越北京时间日期
- 韩国、日本和台湾开闭市时间不同
- 比特币连续交易，不应套用证券市场状态
- 期货交易时段和对应现货指数并不一致

仅把时间戳加 8 小时是不够的。状态判断必须基于交易所本地日期、时区、周末和休市日，再转换为北京时间展示。

### 5.2 交易状态和数据新鲜度必须分开

市场处于交易时间，不代表收到的行情就是实时数据；市场已收盘，也不代表旧行情异常。

项目最终把两个概念分开：

- 市场状态：盘前、LIVE、午间休市、已收盘、假期休市
- 数据状态：当前、延迟、缺失、最近有效快照

这解决了开盘中显示旧行情、休市日误报异常以及闭市数据被错误标为延迟的问题。

### 5.3 假期不能简单归类为周末

韩国制宪节等特殊休市曾被显示为“周末休市”。根因是只知道当天不开盘，却不知道不开盘原因。

最终做法是：

- 维护可更新的主要市场假日日历
- 周六、周日单独判定
- 特殊休市显示“假期休市”
- 数据健康检查根据交易日历判断是否应该有新数据

### 5.4 午间休市的时间不能伪装成收盘时间

A 股 11:30 到 13:00 期间，卡片曾显示当天 15:00，等于展示了尚未发生的收盘时间。修复原则是：

- 午休时保留最近实际行情时间
- 正式闭市后才可显示当日收盘时间
- 卡片状态文案和右下角时间必须来自同一市场状态结果

## 6. 现货和期货参考

在美股、恒生和日经现货闭市时，期货能提供更及时的方向参考，但不能与现货混为一谈。

最终规则是：

- 现货交易中优先现货
- 现货闭市且期货处于活跃状态时，可以显示期货
- 期货必须明确标注“期货 LIVE”
- 收益页的历史区间和最新收盘排名仍使用收盘序列，不使用盘中期货替代
- 期货过期后回到现货收盘，但需要宽限窗口避免状态横跳

### 6.1 状态横跳的根因

页面曾在“已收盘”和“期货 LIVE”之间反复切换。根因通常不是 JSX，而是：

- 前端认为期货过期的时间短于 Worker 刷新间隔
- 某次请求拿到期货，下一次只拿到现货缓存
- 现货和期货分别刷新，快照发布时间不一致

修复方法是统一前后端新鲜度窗口，并以完整快照发布结果做选择，而不是让每张卡片独立猜测。

### 6.2 期货涨跌不能总按昨收计算

部分外盘期货的涨跌基准是上一结算价。直接套用股票的昨收字段会出现三个期货同时 `0.00%` 或与市场显示不一致。

可复用原则：价格、昨收、结算价和涨跌字段必须按品种验证，不能只因为接口字段位置相同就使用同一公式。

## 7. QDII 基金估值模型

### 7.1 最难的问题是“估算哪一天”

早期只显示“T 日估算”，但在周末、盘前、境内外假期错位和官方净值尚未披露时，这个标签容易产生误解。

最终拆分为三个明确概念：

- 最新已出净值：基金管理人已经披露的官方净值及日期
- 待公布估值：所有相关市场已完成交易、但官方净值尚未披露的目标日
- 实时参考：当前境内估值日基于各市场所处阶段计算的参考结果

待公布估值只能使用同一目标日冻结的行情与汇率。实时参考可以组合：

- 已收盘市场的当日收盘价
- 正在交易市场的当前行情
- 尚未开盘市场的最近有效收盘价

卡片必须同时展示目标日期和官方净值日期，不能只显示“盘前”或“盘后”而不说明估值对应哪一天。

### 7.2 日期对齐公式

```text
股票累计涨跌 = 目标日价格 / 官方净值日价格 - 1
汇率累计涨跌 = 目标日汇率 / 官方净值日汇率 - 1

人民币口径涨跌 = (1 + 股票累计涨跌) * (1 + 汇率累计涨跌) - 1
持仓贡献 = 持仓权重 * 人民币口径涨跌
```

### 7.3 未披露部分不能直接忽略

前十大持仓通常只覆盖一部分基金资产。如果简单把已覆盖部分归一化到 100%，等于假设剩余资产与前十大完全同向，容易放大行业集中度。

最终采用残差基准模型：

```text
估算累计涨跌
  = 已披露持仓贡献
  + (1 - 已覆盖权重) * 配置宽基的人民币口径涨跌
```

默认基金根据投资方向配置纳指100或标普500等宽基。只有基准数据不可用时，才降级为覆盖权重归一化。

### 7.4 汇率必须与估值日一致

把实时汇率用于历史目标日，会把目标日之后的汇率变化错误计入基金估值。项目最终保存历史参考汇率，并按官方净值日和目标日分别取值。

这条经验同样适用于任何跨币种收益计算：价格和汇率必须落在同一日期口径，不能一边历史、一边实时。

### 7.5 ETF 联接和 FOF 需要穿透

部分基金披露的是目标 ETF 或其他基金，而不是最终股票。直接把基金代码当作股票行情会导致估算失真。

项目采用三种方式：

- 普通主动基金使用披露股票持仓
- ETF 联接基金优先穿透目标 ETF 的公开组合
- FOF 使用披露基金组合，并在可以获得底层信息时进一步映射

特殊映射必须记录来源和季度，不能永远写死后忘记更新。

### 7.6 校准必须防止过拟合

项目曾尝试用历史估算和实际净值拟合修正。直接对全部历史做线性拟合，看起来误差会下降，但很可能只是样本内过拟合。

最终设置门槛：

- 保存历史估值快照与后续官方结果
- 按时间顺序切分训练和验证样本
- 样本不少于最低数量
- 验证集 MAE 至少显著改善
- 对校准参数设置合理边界
- 不满足条件时继续使用原始模型

校准是可选增强，不应掩盖持仓过期、行情缺失或日期错误。

## 8. 历史、收益和风险数据

### 8.1 历史必须持久化

最初详情弹窗在打开时实时拉取历史，曾出现“暂无历史净值”、只加载近一个月、不同区间都显示同一段数据等问题。

最终做法是：

- Worker 和 backfill 增量维护历史序列
- API 请求只读取 SQLite
- 新增基金时异步补齐可获取的历史数据
- 详情页只按需请求当前基金，不在首页加载全部历史
- 历史不足时明确显示实际覆盖范围

### 8.2 区间收益必须使用同一序列

卡片左下角“今年收益”曾与详情弹窗“今年”不一致。常见根因包括：

- 卡片使用旧缓存，弹窗重新计算
- 一个使用行情涨跌字段，一个使用历史首尾价格
- 起始日选择规则不同
- ETF 除权后一个序列复权、另一个未复权

最终原则是让卡片、收益页、风险页和详情图表共享同一历史序列与区间计算函数，并返回实际起止数据日期。

### 8.3 除权和拆分是高风险异常

ETF 发生份额折算、除权或拆分时，未复权价格可能表现为单日跌去一半，进而污染近月收益、回撤和图表。

项目实际遇到过多个 ETF 因除权导致错误收益，处理方式包括：

- 优先选择数据更稳定、近期无异常折算的替代表的
- 历史接口尽量使用一致复权口径
- 对异常单日跳变做数据质量诊断
- 不能确认时不把错误数字展示为正常收益

替换代码只能解决当前标的，长期仍需要复权因子或异常检测机制。

### 8.4 风险指标保持克制

最终保留：

- 最大回撤
- 收益回撤比
- 上涨交易日胜率

曾加入波动率，但白银近一周出现 `64.04%`，容易被用户理解为区间振幅，实际却是短样本年化波动。由于解释成本高、短区间稳定性差，最终移除。

这说明指标不是越多越好。一个指标如果必须依赖长篇说明才能避免误解，就不一定适合默认表格。

## 9. 性能优化

### 9.1 首次加载为什么慢

早期加载链路包括：

- 市场行情和汇率
- 100 多个基金持仓股票行情
- 17 只基金逐个获取最新净值
- 17 只基金历史、申购状态、规模和费率
- 市场状态和历史收益

即使每个请求只需几百毫秒，串行和重复叠加后也会达到 10 秒以上。增加容器数量不能解决这个问题，因为瓶颈是上游等待和请求编排，不是 CPU 进程数。

### 9.2 实施过的有效优化

- 基金净值由串行改为有上限的并发
- 行情符号合并批量请求，减少网络往返
- 市场、汇率和状态合并为 dashboard/overview 快照
- 概览先显示市场卡片，再加载基金摘要
- 独立基金页按需加载估值和详情
- 收益、风险、关于和诊断页面代码分割
- 基金资料、净值表、历史走势和持仓按标签页懒加载
- 后端启动和 Worker 周期任务预热常用历史摘要
- 历史、收益和风险 API 只读 SQLite
- 浏览器轮询按市场状态动态调整
- Worker 原子发布完整快照，多个用户共享同一结果

### 9.3 最有价值的性能原则

1. 不要在用户请求里抓上游。
2. 不要为了首页可能用到而加载所有详情。
3. 多个用户应共享服务器快照，而不是各自触发同样的公开接口。
4. 数据允许延迟一两分钟时，应优先稳定和可解释，而不是追求秒级刷新。
5. 优化前先记录冷缓存、热缓存、页面首屏和数据完成四种时间。
6. 先消除串行、重复和请求时抓取，再考虑压缩几 KB 的前端代码。

### 9.4 没有盲目实施的优化

- 上游 preconnect 对浏览器无效，因为真正连接上游的是 Flask/Worker
- API gzip 已由生产代理处理时，不应在应用层重复压缩
- 继续拆分很小的组件只会增加 chunk 管理成本
- 无限提高并发会触发东方财富等接口限频，不能只追求本地耗时

## 10. UI 和交互经验

### 10.1 首页应先提供可用产品，不做营销页

首页直接展示全球市场和基金摘要，没有增加传统 landing page。对于高频查看型工具，用户最关心的是数据，而不是功能介绍。

### 10.2 简洁卡片与详情分层

基金卡片曾同时展示成立日期、规模、费率、申购状态、区间收益、覆盖率、缺失行情和估值，导致首页拥挤且加载慢。

最终分层：

- 概览基金卡片只展示最新官方净值、涨跌和日期
- 基金页卡片优先展示待公布估值、实时参考和官方净值
- 规模、费率、申购状态、持仓、净值表和走势放入展开详情

“默认简洁，详情按需”同时改善了视觉和性能。

### 10.3 排名信息必须和排序口径一致

TOP/LOW 标签曾与排序按钮、官方净值和估算模式产生混淆。最终把名次与序号合并，并根据当前排序口径重新计算。

任何排行榜都应明确：

- 排什么指标
- 使用什么日期
- 高到低还是低到高
- 缺失数据如何放置
- 卡片上的强调色是否跟随当前口径

### 10.4 移动端表格不能靠隐藏关键列解决

收益和风险页早期为了适配移动端隐藏后续列，导致用户无法查看完整数据。后来改为：

- 排名和名称列固定
- 第一屏保证排名、名称和主指标完整可见
- 次要指标通过横向滚动访问
- 表头、列宽和滚动容器使用稳定尺寸
- 在 320px 和 390px 视口都做浏览器测试

### 10.5 全局一致不等于所有页面完全相同

日期、状态和汇率对概览、基金、收益和风险页面有意义，但关于页是静态说明页面。最终关于页保留品牌和导航，移除行情元信息及对应轮询。

一致性应服务于信息语义，不能为了形式统一而增加无关内容。

## 11. 可靠性、安全和运维

### 11.1 健康接口分层

- `/api/health`：进程是否存活
- `/api/ready`：SQLite 和必要结构是否可用
- `/api/status`：公开的汇总刷新状态
- `/api/diagnostics/quotes`：受令牌保护的详细诊断

公开页面不直接暴露详细异常列表、上游内部错误和数据库结构。

### 11.2 基金管理默认关闭

自定义基金管理具有上游抓取和数据库写入能力，不能只在前端隐藏按钮。

最终保护包括：

- 生产环境默认关闭
- 开启后仍需独立管理令牌
- 后端校验六位基金代码和基金类型
- 限制自定义基金数量和请求频率
- 非默认基金 API 必须携带授权
- 基金列表保存在当前浏览器，管理令牌仅保存在当前浏览器会话，不写入仓库或持久化数据

### 11.3 数据库维护

- SQLite 版本化迁移只向前执行
- 每天在线备份一次
- 同时按天数和最多文件数清理
- 恢复前自动备份当前数据库
- 定期 WAL checkpoint 和 `PRAGMA optimize`
- `VACUUM` 只在离线维护时执行

备份策略从频繁、长期保留调整为每天一次、最多三份，避免小服务器磁盘被可重复备份占满。

### 11.4 CI 和线上验收

提交前不仅运行 TypeScript 构建，还包括：

- Python 后端单元测试
- Vitest 组件和逻辑测试
- 独立兼容逻辑测试
- Playwright 桌面和移动端测试
- Docker 镜像构建
- 临时 Compose 环境健康和就绪检查
- SQLite 完整性检查
- SPA 深链接检查

生产更新后还要检查：

- 三个容器状态
- `/api/health` 和 `/api/ready`
- Worker 首轮任务是否完成
- 概览、基金、收益、风险和关于页是否返回 200
- 浏览器 console、pageerror 和 requestfailed
- 桌面和移动端是否存在页面级横向溢出

## 12. 典型问题、根因和修复

| 现象 | 根因 | 最终处理 | 可复用经验 |
|------|------|----------|------------|
| 基金历史只到 1 个月或 3 个月 | 接口分页和缓存截断 | 后台全量回填后增量维护 | 历史范围不能由详情请求临时决定 |
| 半年、1年、5年图表相同 | 实际数据覆盖不足但 UI 仍切换范围 | 返回真实覆盖日期并按已保存序列裁剪 | 控件状态变化不代表数据真的变化 |
| 卡片今年收益和详情不一致 | 两处使用不同缓存或公式 | 共用历史序列和区间计算 | 派生指标必须单一来源 |
| ETF 近月收益异常 | 除权、拆分或未复权数据 | 更换异常标的并加强诊断 | 单日大跳变要先做公司行为排查 |
| 美股指数最新收益为 0 | 闭市行情字段被当成有效日涨跌 | 收益页改用最近两个收盘点 | 当前行情字段不等于历史收益 |
| 期货涨跌同时为 0 | 错用昨收而非结算价 | 按品种选择正确基准字段 | 解析器需要样本和回归测试 |
| 现货与期货状态横跳 | 新鲜度窗口小于刷新周期 | 统一窗口并增加宽限时间 | 状态机必须匹配数据生产节奏 |
| 日经显示长期错误旧点位 | 现货数据源异常但被当作有效 | 拒绝异常源，交易中使用可靠现货，闭市使用期货参考 | 有值不代表值可信 |
| 韩国开盘时间延迟一小时 | 上游时间的时区解释错误 | 使用交易所本地时区后转北京时间 | 不要对无时区时间戳直接加固定小时 |
| 韩国假期显示周末休市 | 只判断是否不开盘 | 引入假日日历和原因分类 | 状态需要原因，不只是布尔值 |
| A 股盘前显示 0 | 集合竞价前接口返回零字段 | 过滤零值并保留最近有效收盘 | 异常值不能覆盖好缓存 |
| A 股午休显示 15:00 | 用预期收盘时间代替实际行情时间 | 午休保留 11:30 附近实际时间 | 展示时间必须是事实，不是计划时间 |
| 周末估值语义混乱 | 实时行情与目标净值日未分离 | 拆分待公布估值和实时参考 | 所有估值先回答“哪一天” |
| 新基金只有 20 天净值 | 新增流程只获取首页数据 | 新增后异步回填历史、资料和持仓 | 自定义实体要走与默认实体相同的数据流水线 |
| 首页基金加载 10 秒以上 | 串行抓取、重复行情、请求时补历史 | 并发、批量、快照和 Worker | 增加服务器进程无法修复上游串行等待 |
| 风险页比收益页更慢 | 页面进入后才重复计算和取历史 | 预计算摘要并按页面加载 | 已有数据也可能因派生计算而慢 |
| 移动端表格只能看到两列 | 固定列太宽或隐藏后续列 | 收紧名称列并支持横向滚动 | 移动端要定义第一屏主指标 |
| 持仓表头和数据错位 | 单元格对齐规则和列定义不一致 | 统一 grid/table 列宽与 text-align | 表格对齐应由列模型控制 |
| 浏览器测试无页面但返回代理 502 | 本机代理误判 5173 已启动 | 显式启动生产预览并注入 E2E API 地址 | 测试环境也要验证实际监听端口 |

## 13. 做过但最终没有保留的功能

### 13.1 实时分钟图

项目曾加入指数和资产的实时分钟行情。后来移除，原因是：

- 免费公开分钟接口稳定性不足
- 时区和交易时段问题明显增加
- 页面已定位为估值与区间观察，不是交易终端
- 高频抓取成本与实际价值不匹配

历史日线加当前卡片更符合产品定位。

### 13.2 估值可信度和净值滞后标签

可信度百分比容易被理解成统计置信度，但它最初更多反映行情覆盖，不等于估值准确率。净值滞后也可以直接通过日期判断。

最终删除这些标签，把空间留给目标日期、官方净值日和行情状态等可验证事实。

### 13.3 基金回测 UI

回测对开发估值模型有价值，但普通用户难以正确解释历史持仓缺失、幸存者偏差和样本内校准。最终保留后端对账与校准能力，移除前端回测入口。

### 13.4 基金列表导入导出和 CSV

默认基金数量有限，自定义配置只存在当前浏览器。导入导出增加格式校验、安全和兼容成本，实际使用价值较低，因此移除。

### 13.5 美债利率、恐慌贪婪指数等宏观指标

这些指标本身有价值，但当时可用来源不够实时或稳定，放在 Header 还会稀释核心行情。项目选择先不加入，而不是为丰富页面使用质量较低的数据。

### 13.6 非 QDII 基金和大量重复指数基金

加入更多基金很容易，但会增加净值、资料、持仓和历史维护成本，也会稀释“海外市场相关 QDII”的主题。项目优先保持代表性，而不是追求数量。

## 14. 当前局限和技术债

### 14.1 数据源没有 SLA

公开接口可能改变字段、增加频率限制或停止访问。缓存和兜底只能提高韧性，无法替代正式授权数据。

### 14.2 持仓天然滞后

基金估算主要依赖季度披露，无法知道基金经理盘中调仓、现金、衍生品和申赎变化。即使算法完全正确，输入也不是基金实时组合。

### 14.3 特殊基金穿透仍需维护

目标 ETF、FOF 和特殊组合可能需要单独映射。季度更新后应自动检测配置是否仍有效，目前部分穿透仍依赖规则和人工复核。

### 14.4 假日日历需要持续更新

本地假日配置提高了确定性，但新年份需要维护。未来可以评估稳定的交易所日历源，同时保留本地缓存，避免运行时依赖。

### 14.5 前端 App 仍然偏集中

页面已经懒加载，但基金管理、路由和多页数据状态仍有一部分集中在 `App.tsx`。继续增加页面前，适合拆出应用路由层和基金管理状态模块。

### 14.6 可变 Release 标签不适合长期版本管理

项目迭代中多次覆盖同一个版本标签，适合快速试验，但会改变已发布版本的含义，也不利于回滚和审计。

更规范的做法是：

- 发布标签一旦公开就不再移动
- 小修复递增补丁版本
- Release 说明只描述该不可变提交
- 部署记录保存提交哈希，而不是只保存版本名

### 14.7 关于页更新记录需要人工维护

关于页只记录重大功能变化，不同步字号、间距、文案和普通缺陷修复。它是面向用户的演进摘要，不是 Changelog。

## 15. 可复用工作流

### 15.1 新增一个市场或数据源

1. 在本地和生产网络分别测试可访问性。
2. 保存至少一个正常、休市、异常和缺字段样本。
3. 明确当前、昨收、结算、时间和时区字段。
4. 确认是否有历史数据及复权口径。
5. 增加统一 symbol 和市场配置。
6. 增加交易时段、午休、周末和假日判断。
7. 后端解析为统一行情结构。
8. 写入快照、历史和健康诊断。
9. 增加解析、市场状态和异常值测试。
10. 在生产服务器验证时间、价格和刷新间隔。

### 15.2 新增一个基金

1. 强校验六位代码和基金类型。
2. 获取官方名称、最新净值和历史净值。
3. 获取成立日期、规模、费率和申购状态。
4. 获取最新正式季度持仓并记录报告期。
5. 判断普通股票、目标 ETF 或 FOF 穿透方式。
6. 为每个持仓映射市场、币种和行情源。
7. 配置未披露部分的宽基基准。
8. 增量回填持仓价格和汇率基准。
9. 计算行情覆盖和缺失项，但不把覆盖率伪装成准确率。
10. 验证官方净值、待公布目标日和实时参考日期。

### 15.3 排查加载慢

1. 区分白屏时间、市场可见时间和全部数据完成时间。
2. 分别测试完全冷启动、服务器热缓存和浏览器二次访问。
3. 列出页面触发的全部 API，不凭感觉判断。
4. 查找串行请求、重复 symbols 和重复历史加载。
5. 检查 API 是否在请求中访问上游。
6. 查看 Worker 最近成功时间和快照更新时间。
7. 优先消除上游等待，再优化传输体积。
8. 修改后同时在本地和生产网络测量。

### 15.4 发布和部署

1. 检查 `git diff` 和工作树，避免覆盖无关修改。
2. 运行后端、前端单元测试和生产构建。
3. 运行桌面与移动端 Playwright 测试。
4. 使用包含主要变化的 Conventional Commit。
5. 推送后确认 GitHub CI 成功。
6. 服务器确认工作树干净并快进到指定提交。
7. 使用现有 `.env` 重建 Compose 服务。
8. 检查容器、健康、就绪、Worker 和数据库状态。
9. 用真实域名检查每个公开页面。
10. 收集 console、pageerror、requestfailed 和横向溢出结果。

## 16. 协作方式中的经验

### 16.1 小步改动适合 UI，完整闭环适合数据问题

字号、间距和文案可以快速迭代并截图确认。数据日期、估值和缓存问题则必须完成：复现、定位、后端修复、数据刷新、测试、部署和线上核对，不能只修改前端显示。

### 16.2 用户观察是重要监控来源

很多问题只在特定真实时段出现，例如：

- A 股开盘前返回零值
- 午间休市显示未来收盘时间
- 韩国节假日状态错误
- 美股期货在刷新边界横跳
- QDII 官方净值在特定日期未更新

自动测试很难覆盖所有真实上游状态。用户反馈应转化为固定样本和回归测试，而不是只做一次性修复。

### 16.3 截图用于视觉，结构化指标用于性能

截图适合确认对齐、间距、层级和移动端第一屏。性能判断必须使用请求链路、响应耗时、缓存命中和 Worker 时间，不能只看“感觉变快”。

### 16.4 其他模型的评估适合作为第二视角

多个模型曾提出性能和架构建议，其中一些准确指出了串行基金请求和重复行情，另一些建议在当前架构中已经实现或不适用。

最有效的协作方式不是比较模型结论，而是：

- 提取可以验证的假设
- 对照当前代码和生产链路
- 用测试或计时确认
- 只实施对当前瓶颈有收益的部分

## 17. 最终总结

这个项目最有价值的不是增加了多少指数、基金和页面，而是逐步形成了几个稳定原则：

1. 数据时间和目标日期必须先于计算公式明确。
2. 页面请求只读本地快照，公开上游由后台刷新。
3. 不可靠的数据宁可显示缺失，也不要伪装成正常行情。
4. 现货、期货、官方净值和估算结果必须明确区分。
5. 详情按需加载，首页优先提供可快速扫描的核心信息。
6. 指标和功能不是越多越好，解释成本也是产品成本。
7. 多市场项目必须把交易日历、时区和数据新鲜度作为核心领域逻辑。
8. 每个生产问题最终都应沉淀为解析规则、状态机或回归测试。
9. 小型项目也需要健康检查、备份、CI 和可重复部署。
10. 对外展示保持简洁，对内诊断保持充分。

这些原则可以直接复用于其他行情看板、基金分析、跨市场数据聚合和后台定时刷新项目。
